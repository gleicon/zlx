# Plan 12-03: TurboQuant Verification and Fix

## Goal
Verify TurboQuant KV cache compression is actually working and achieving the claimed 4.6x memory reduction. Fix if broken or incomplete.

## Background

**Current Status:** Phase 7 (TurboQuant Integration) is marked complete in the roadmap, but:
- No verification that compression is applied
- No measurement of actual memory savings
- User reports that 128K context still OOMs on 16GB machines
- PRD assumption that TurboQuant provides C/C++ API was wrong (it's Python only)

**What TurboQuant Does:**
- Compresses KV cache using 2-bit quantization with Hadamard rotation
- Achieves 4.6x memory reduction vs FP16
- Enables 128K context on 16GB machines
- Critical for MoE models with large KV requirements

**Test 1: Memory Measurement**

    const allocator = std.testing.allocator;
    
    // Create KV cache for 8192 context, 27 layers, 2048 hidden

### Task 3: Implement TurboQuant (2h)

**Option A: Use MLX Built-in Quantization (Recommended)**

MLX has native KV cache quantization:
```zig
fn createQuantizedKVCache(
    allocator: Allocator,
    max_seq_len: usize,
    num_layers: usize,
    hidden_size: usize,
    bits: u8, // 2, 4, or 8
) !QuantizedKVCache {
    // Use MLX's quantization primitives
    // Store as int2/int4/int8 instead of float16
}
```

**Advantages:**
- No custom Metal kernels needed
- Already optimized in MLX
- Easy to implement

**Implementation:**
```zig
pub const QuantizedKVCache = struct {
    k_cache: []mlx.Array, // Quantized K tensors per layer
    v_cache: []mlx.Array, // Quantized V tensors per layer
    scale: []f32, // Per-layer scaling factors
    config: CacheConfig,
    
    pub fn store(self: *QuantizedKVCache, layer: usize, pos: usize, k: mlx.Array, v: mlx.Array) !void {
        // Quantize and store
        var k_q = mlx.arrayNew();
        var v_q = mlx.arrayNew();
        
        // Use MLX quantization ops
        try mlx.quantize(&k_q, k, self.config.bits, self.scale[layer]);
        try mlx.quantize(&v_q, v, self.config.bits, self.scale[layer]);
        
        // Store quantized arrays
        self.k_cache[layer] = k_q;
        self.v_cache[layer] = v_q;
    }
    
    pub fn retrieve(self: *QuantizedKVCache, layer: usize, pos: usize, k: *mlx.Array, v: *mlx.Array) !void {
        // Dequantize and return
        try mlx.dequantize(k, self.k_cache[layer], self.config.bits, self.scale[layer]);
        try mlx.dequantize(v, self.v_cache[layer], self.config.bits, self.scale[layer]);
    }
};
```

**Option B: Port TurboQuant Python Kernels (High Effort)**

TurboQuant's Python Metal kernels:
```python
# From turboquant-mlx repository
mx.fast.metal_kernel("hadamard_rotation")(...)
mx.fast.metal_kernel("quantize_2bit")(...)
```

**Problems:**
- No C/C++ API to bind
- Would need to rewrite in Zig or C
- Significant effort (20+ hours)

**Decision:** Use Option A (MLX native) unless Option B proves necessary for quality.

## Configuration

**Default Behavior:**
- Auto-enable on systems with < 16GB RAM
- Use 2-bit quantization (4.6x compression)
- Allow override via CLI flag: `--kv-compression 4bit` or `--no-kv-compression`

## Success Criteria

- [ ] KV cache memory measured and logged
- [ ] 4K context uses < 500MB (vs ~2GB uncompressed)
- [ ] 16K context uses < 2GB (vs ~8GB uncompressed)
- [ ] 128K context uses < 16GB (vs ~60GB uncompressed)
- [ ] Quality test: perplexity increase < 5%
- [ ] Auto-enables on 8GB and 16GB machines
- [ ] Can be disabled with `--no-kv-compression`

## Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| MLX quantization not available in v0.1.2 | Upgrade to mlx-c v0.4.x (Phase 11) |
| Quality degradation unacceptable | Use 4-bit instead of 2-bit (2.3x vs 4.6x) |
| Speed impact too high | Profile and optimize hot paths, cache dequantized values |
| Different compression for K vs V | V is more sensitive, use 4-bit for V, 2-bit for K |

## Dependencies

- mlx-c v0.4.x with quantization primitives
- DeepSeek MLA layer (to integrate compression)
- Memory profiling tools (Activity Monitor or jemalloc stats)

## Notes

- TurboQuant was over-engineered for this project
- MLX native quantization achieves same goal with less effort
- Focus on 2-bit for maximum compression; fallback to 4-bit if quality issues
- Test on actual 16GB MacBook before declaring complete
