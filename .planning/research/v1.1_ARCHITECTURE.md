# Architecture Patterns: zlx v1.1 Features

**Project:** zlx — Zig LLM Inference Server v1.1  
**Domain:** Advanced features architecture (multi-model, prompt caching, TurboQuant, performance optimizations)  
**Researched:** 2026-04-01  
**Confidence:** HIGH (patterns derived from MLX.zig source, OpenAI API specs, local LLM server architectures)

---

## Executive Summary

zlx v1.1 extends the minimal v1.0 architecture (4-file Zig project) to support advanced features while maintaining the core principle: single static binary, no Python runtime. The architecture adds six new components: model manager, KV cache persistence, TurboQuant integration, speculative decoding, sampling parameter pipeline, and download manager. All components remain Zig-native and MLX-compatible. Key insight: Multi-model support and prompt caching are orthogonal features — they can be implemented independently and in any order. TurboQuant requires the most invasive changes to the KV cache layer.

### model_manager.zig (NEW)

**Responsibility:** Manage model lifecycle, registry, and memory budget.

**Public Interface:**
```zig
pub const ModelManager = struct {
    pub fn init(allocator: std.mem.Allocator, config: Config) !ModelManager;
    pub fn deinit(self: *ModelManager) void;
    
    // Registry
    pub fn scanModels(self: *ModelManager) !void;
    pub fn listModels(self: *ModelManager) []const ModelInfo;
    pub fn resolveAlias(self: *ModelManager, alias: []const u8) ?[]const u8;
    
    // Lifecycle
    pub fn loadModel(self: *ModelManager, path: []const u8) !void;
    pub fn unloadCurrentModel(self: *ModelManager) void;
    pub fn getCurrentModel(self: *ModelManager) ?*LoadedModel;
    
    // Memory
    pub fn checkMemoryBudget(self: *ModelManager, model_size: usize) bool;
    pub fn getAvailableMemory(self: *ModelManager) usize;

**State Machine:**
```

     └──────────────── unload() ────────────────────┘

### spec_decode.zig (NEW)

**Responsibility:** Speculative decoding for faster generation.

**Algorithm:**
```zig
pub fn generateSpeculative(
    target_model: *Transformer,
    draft_model: *Transformer,
    prompt: []const u32,
    max_tokens: usize,
    num_draft_tokens: usize,
) ![]u32 {
    var result = std.ArrayList(u32).init(allocator);
    var current_prompt = prompt;
    
    while (result.items.len < max_tokens) {
        // Draft model generates N tokens
        const draft_tokens = try draft_model.generate(current_prompt, num_draft_tokens);
        
        // Target model verifies all draft tokens in one forward pass
        const verified_count = try verifyDraftTokens(target_model, current_prompt, draft_tokens);
        
        // Accept verified tokens
        try result.appendSlice(draft_tokens[0..verified_count]);
        
        // If any rejected, target model generates the correct next token
        if (verified_count < draft_tokens.len) {
            const corrected_token = try target_model.generateNext(current_prompt);
            try result.append(corrected_token);
        }
        
        current_prompt = result.items;
    }
    
    return result.toOwnedSlice();
}
```

## Data Flow: Multi-Model Support

### Scenario: Switch from Model A to Model B

```
1. Client: POST /v1/models/switch { "model": "model-b" }
                    ↓
2. server.zig: Parse request, call model_manager.switchModel()
                    ↓
3. model_manager.zig:
   a. Check if Model B is available in registry
   b. Query available memory → is there room?
   c. If no room: error 507 (Insufficient Storage)
   d. If room: proceed
                    ↓
4. Unload Model A:
   a. inference.zig: Stop current generation (if any)
   b. mlx_array_free() on all model weights
   c. mlx_synchronize() to ensure GPU memory released
                    ↓
5. Load Model B:
   a. Transformer.init() for Model B
   b. Load weights from disk → Metal GPU memory
   c. Update "current model" pointer
                    ↓
6. Response: { "status": "ok", "model": "model-b" }
```

## Data Flow: Prompt Caching

### Scenario: First Request (Cache Miss)

```
1. Client: POST /v1/chat/completions
   { "cache_key": "project-context", "save_cache": true, "messages": [...] }
                    ↓
2. server.zig: Parse cache_key
                    ↓
3. Check ~/.zlx/cache/ — no existing cache for "project-context"
                    ↓
4. Normal generation:
   a. Tokenize messages
   b. Generate response (fills KV cache)
   c. Stream tokens to client
                    ↓
5. After generation completes:
   a. KVCache.save("~/.zlx/cache/model-hash/project-context.cache")
   b. mlx_save() for K and V arrays
                    ↓
6. Response includes: { "cache_created": "project-context" }
```

### Scenario: Second Request (Cache Hit)

```
1. Client: POST /v1/chat/completions
   { "cache_key": "project-context", "messages": [...] }
                    ↓
2. server.zig: Parse cache_key
                    ↓
3. Check ~/.zlx/cache/ — cache exists!
                    ↓
4. Load cache:
   a. KVCache.load("project-context.cache")
   b. mlx_load() for K and V arrays
   c. Set generation state with loaded cache
                    ↓
5. Resume generation from cached position:
   a. Only tokenize NEW messages (not cached prefix)
   b. Continue generation
   c. TTFT: <100ms (vs 5-30s without cache)
                    ↓
6. Response includes: { "cache_hit": "project-context" }
```

## Data Flow: TurboQuant Integration

### Scenario: Generate with TurboQuant Enabled

```
1. Client: POST /v1/chat/completions
   { "model": "qwen2.5-coder", "turboquant": true, "messages": [...] }
                    ↓
2. server.zig: Parse turboquant flag
                    ↓
3. inference.zig: Initialize TurboQuantKVCache instead of StandardKVCache
   a. Allocate quantized storage (4.6x smaller)
   b. Initialize Hadamard rotation tables
                    ↓
4. Generation loop:
   a. Transformer.forward() computes new K, V
   b. KVCache.update(K, V):
      i.   Hadamard rotation: rotate K, V vectors
      ii.  Lloyd-Max quantization: map to 3-bit centroids
      iii. Store indices + norms (compressed)
                    ↓
   c. Attention computation:
      i.   Dequantize on-demand via Metal kernel
      ii.  Fused Q@K^T computation
      iii. Softmax, V multiplication
                    ↓
5. Result: 4.6x memory savings, 60-98% speed vs FP16
```

## Architectural Patterns

### Pattern 1: Strategy Pattern for KV Cache Backends

**What:** Pluggable KV cache implementations with common interface.

**When:** When you need multiple algorithms (standard, quantized, persistent) that are interchangeable.

**Benefits:**
- Runtime selection via config/flag
- Easy to add new backends
- Test implementations independently

**Implementation:**
```zig
const KVCache = struct {
    vtable: *const VTable,
    ctx: *anyopaque,
    
    pub fn update(self: KVCache, keys: mlx.Array, values: mlx.Array) void {
        self.vtable.update(self.ctx, keys, values);
    }
    // ... other methods
};

// Usage
const cache: KVCache = if (use_turboquant)
    TurboQuantKVCache.create(...)
else if (use_persistent)
    PersistentKVCache.create(...)
else
    StandardKVCache.create(...);
```

### Pattern 2: State Machine for Model Lifecycle

**What:** Explicit states for model loading/unloading with valid transitions.

**When:** Complex async operations with clear phases.

**Benefits:**
- Prevents invalid operations (e.g., generate while loading)
- Clear error messages for invalid states
- Easy to add progress tracking

**States:**
```
Unloaded → Loading → Ready → Generating → Ready → Unloading → Unloaded
```

### Pattern 3: Pipeline for Sampling

**What:** Chain of responsibility for sampling parameter application.

**When:** Multiple sequential transformations of data.

**Benefits:**
- Easy to add/remove stages
- Each stage is testable independently
- Clear order of operations

**Pipeline:**
```zig
pub fn sample(logits: mlx.Array, config: SamplingConfig) u32 {
    var modified = logits;
    modified = applyTemperature(modified, config.temperature);
    modified = applyTopK(modified, config.top_k);
    modified = applyTopP(modified, config.top_p);
    modified = applyMinP(modified, config.min_p);
    modified = applyPenalties(modified, config, context);
    modified = applyLogitBias(modified, config.logit_bias);
    return sampleToken(modified);
}
```

### Pattern 4: Background Worker for Downloads

**What:** Separate thread for long-running I/O operations.

**When:** Operations that would block the main thread (HTTP downloads).

**Benefits:**
- Inference remains responsive
- Progress reporting
- Cancellation support

**Implementation:**
```zig
// Download thread
fn downloadWorker(queue: *DownloadQueue) void {
    while (true) {
        const task = queue.pop() orelse break;
        downloadWithProgress(task) catch |e| {
            task.onError(e);
        };
        task.onComplete();
    }
}

// Main thread
pub fn startDownload(task: DownloadTask) void {
    download_queue.push(task);
    // Returns immediately, doesn't block
}
```

## Anti-Patterns to Avoid

### Anti-Pattern 1: Global Model State Without Mutex

**What:** Multiple threads accessing the current model without synchronization.

**Why Bad:** Race conditions during model switch; corrupted generation state.

**Instead:** Single mutex around model manager access:
```zig
var model_mutex: std.Thread.Mutex = .{};

pub fn handleRequest(req: Request) !void {
    model_mutex.lock();
    defer model_mutex.unlock();
    // ... use model
}
```

### Anti-Pattern 2: Unbounded Cache Growth

**What:** Saving every prompt cache forever without eviction.

**Why Bad:** Disk fills up; cache lookup slows down.

**Instead:** LRU eviction with max size:
```zig
const CacheManager = struct {
    max_size_bytes: usize,
    entries: std.AutoHashMap([]const u8, CacheEntry),
    lru_list: std.TailQueue(CacheEntry),
    
    pub fn saveCache(self: *CacheManager, key: []const u8, data: []const u8) !void {
        // If over limit, evict oldest
        while (self.current_size + data.len > self.max_size_bytes) {
            const oldest = self.lru_list.popFirst();
            self.remove(oldest.key);
        }
        // Save new entry
        self.entries.put(key, .{ .data = data, .node = self.lru_list.append(...) });
    }
};
```

### Anti-Pattern 3: Synchronous Model Loading in Request Handler

**What:** Loading a new model while handling an HTTP request.

**Why Bad:** Request times out; client sees 504 Gateway Timeout.

**Instead:** Async model loading with status endpoint:
```zig
pub fn handleLoadModel(req: Request, res: Response) !void {
    // Return immediately with "loading" status
    try res.json(.{ .status = "loading", .model = req.model });
    
    // Start background load
    try model_manager.loadModelAsync(req.model);
}

// Client polls GET /v1/models/status until ready
```

### Anti-Pattern 4: Cross-Model KV Cache Reuse

**What:** Using cached KV from Model A with Model B.

**Why Bad:** Different tokenizers, different layer dimensions — garbage output.

**Instead:** Include model hash in cache key:
```zig
const cache_key = std.fmt.allocPrint(allocator, "{s}:{s}", .{
    model_hash,
    prompt_hash
});
```
