# Feature Landscape: zlx v1.1

**Project:** zlx — Zig LLM Inference Server v1.1  
**Domain:** Advanced features for local LLM inference on Apple Silicon  
**Researched:** 2026-04-01  
**Confidence:** HIGH (OpenAI API patterns verified, MLX ecosystem analyzed, competitive landscape surveyed)

---

## Executive Summary

zlx v1.1 adds seven feature categories that transform the minimal v1.0 server into a competitive local LLM platform. The feature prioritization is driven by three factors: OpenAI API compatibility (what clients expect), competitive differentiation (what sets zlx apart), and MLX ecosystem capabilities (what's technically feasible). Key insight: Many "advanced" features are actually table stakes for modern local LLM servers — logprobs, stop sequences, and prompt caching are expected by agentic coding tools. TurboQuant remains the primary differentiator but requires non-trivial Metal kernel extraction.

---

## Feature Categories

### 1. TurboQuant KV-Cache Compression

**Value Proposition:** 4.6x KV cache compression at ~60-98% FP16 speed (varies by config), enabling 32k+ context on 7B-14B models with 4-bit weights. This is zlx's primary technical differentiator — no other single-binary Zig server offers this.

**Table Stakes vs Differentiator:** Differentiator — not required for basic functionality, but core to zlx's "extended context" value proposition.

| Config | Speed | Cache Size | Compression | Quality |
|--------|-------|------------|-------------|---------|
| FP16 baseline | 52.1 tok/s | 14.0 MB | 1.0x | baseline |
| TQ3 adaptive (4+4) | 30.7 tok/s | 5.9 MB | 2.4x | good |
| TQ3 adaptive (6+6) | 33.0 tok/s | 7.5 MB | 1.9x | good |

**Implementation Complexity:** HIGH  
**Dependencies:** Metal kernel extraction and compilation  
**User Impact:** Enables long-context coding tasks (full file analysis, multi-file reasoning)

**MVP vs Full Implementation:**
- **MVP:** Layer-adaptive mode (first/last N layers in FP16, middle in TQ3)
- **Full:** User-configurable bit depth (1-4 bits), custom layer selection, fused attention optimization

### 2. Multi-Model Support

**Value Proposition:** Switch between models (e.g., Qwen2.5-Coder for coding, Llama-3.2 for general chat) without restarting the server. Critical for users who want one server instance serving multiple use cases.

**Table Stakes vs Differentiator:** Table stakes — llama.cpp server, Ollama, and mlx-lm server all support this.

**Feature Breakdown:**

| Sub-Feature | Complexity | Priority | Notes |
|-------------|------------|----------|-------|
| Model registry (scan `./models/` on startup) | LOW | P1 | List available models for `/v1/models` endpoint |
| Hot-load new model | MEDIUM | P1 | Load model while server is running via API call |
| Hot-unload model | MEDIUM | P2 | Free memory when switching |
| Memory pressure handling | MEDIUM | P2 | Refuse load if insufficient RAM |
| Model aliases (`--served-model-name`) | LOW | P1 | Map short names to full paths |

**API Additions:**
```
POST /v1/models/load        # Load a model by path or HF repo
POST /v1/models/unload      # Unload current model
POST /v1/models/switch      # Atomic switch to new model
GET  /v1/models/status      # Currently loaded model + memory stats
```

**OpenAI API Compatibility:** Extension beyond standard — OpenAI doesn't have multi-model servers. Follow mlx-lm server patterns.

### 3. Prompt Caching (KV-Cache Persistence)

**Value Proposition:** Eliminate TTFT (Time To First Token) for repeated contexts. Critical for:
- Agentic workflows (same system prompt + context every request)
- Chat history (reuse KV cache from previous turns)
- RAG pipelines (same retrieved documents repeated)

**Table Stakes vs Differentiator:** Becoming table stakes — vLLM has prefix caching, TensorRT-LLM has KV cache reuse, mlx-lm server does not have it yet.

**Key Metrics:**
- Without cache: TTFT = O(prompt_length) — can be 5-30 seconds for 32k context
- With cache: TTFT = O(new_tokens_only) — typically <1 second

**Implementation Modes:**

| Mode | Description | Complexity | Use Case |
|------|-------------|------------|----------|
| **Automatic prefix matching** | Server automatically detects common prompt prefixes and reuses KV cache | HIGH | Chat history, incremental prompts |
| **Explicit cache key** | Client provides `cache_key` parameter; server loads/saves KV cache by key | MEDIUM | Agentic workflows, fixed contexts |
| **Manual cache management** | API endpoints for save/load/delete cache entries | LOW | Power users, debugging |

**Recommended Approach:** Start with explicit cache key (client-controlled), add automatic prefix matching later.

**API Additions:**
```json
// Request with cache
POST /v1/chat/completions
{
  "model": "qwen2.5-coder",
  "cache_key": "project-context-v1",  // Load cached KV for this key
  "save_cache_key": "project-context-v2", // Save KV under new key
  "messages": [...]
}

// Cache management endpoints
GET    /v1/cache           # List cache entries
DELETE /v1/cache/{key}      # Delete specific cache
DELETE /v1/cache            # Clear all cache
```

### 4. Web UI

**Value Proposition:** Browser-based chat interface for users who prefer GUI over API/CLI. Enables non-technical users, testing, and casual use.

**Table Stakes vs Differentiator:** Table stakes — expected by users coming from Ollama, LM Studio, text-generation-webui.

**Critical Decision: Build vs Integrate**

| Approach | Effort | Maintenance | Quality | Recommendation |
|----------|--------|-------------|---------|----------------|
| **Integrate Open WebUI** | LOW | LOW (external) | HIGH (46K stars) | **YES** |
| Integrate Text Generation WebUI | LOW | LOW | MEDIUM | Alternative |
| Custom Zig/WASM UI | HIGH | HIGH | UNKNOWN | NO |
| Static HTML + JS | MEDIUM | MEDIUM | LOW | NO |

**Open WebUI Integration:**
- Open WebUI is a self-hosted, feature-rich web interface
- Already OpenAI-compatible — just point it at zlx
- Provides chat, model switching, history, RAG, tool calling UI
- Users install separately: `docker run -p 3000:8080 ghcr.io/open-webui/open-webui`

**zlx Changes Required:**
- None for basic integration (already OpenAI-compatible)
- Add CORS headers if accessing from different origin: `Access-Control-Allow-Origin: *`

**Feature Parity:** Open WebUI provides more features than any custom UI we could build in reasonable time:
- Chat history with search
- Multiple model support
- Document upload and RAG
- Tool calling UI
- Voice input/output
- Mobile responsive

### 5. API Improvements

**Purpose:** Full OpenAI API compatibility so zlx works with any OpenAI client (OpenCode, Continue.dev, ChatGPT-Next-Web, etc.).

#### 5.1 Stop Sequences

**Status:** Partial in v1.0 (EOS token only) → Full in v1.1

**OpenAI Spec:** `stop` parameter — string or array of strings. Generation stops when any sequence is matched.

**Implementation:**
```zig
// After each token generation, check if generated text ends with any stop sequence
for (stop_sequences) |seq| {
    if (std.mem.endsWith(u8, generated_text, seq)) {
        // Truncate at stop sequence boundary
        // Set finish_reason: "stop"
        break;
    }
}
```

**Complexity:** LOW

#### 5.2 Logprobs

**OpenAI Spec:** `logprobs: integer` (1-10) — return log probabilities for top N tokens at each position.

**Use Cases:**
- Token probability visualization
- Uncertainty quantification
- Prompt debugging
- Alternative token exploration

**Response Format:**
```json
{
  "choices": [{
    "logprobs": {
      "token_logprobs": [-0.5, -1.2, -0.1],
      "tokens": ["Hello", " world", "!"],
      "top_logprobs": [
        {"Hello": -0.5, "Hi": -1.5, "Hey": -2.0},
        {" world": -1.2, " there": -2.0, "!": -3.0}
      ]
    }
  }]
}
```

**MLX Integration:** `mlx.softmax(logits)` produces probabilities; track top-k during sampling.

**Complexity:** MEDIUM

#### 5.3 Temperature & Sampling Improvements

**Already Supported (MLX.zig):**
- `temperature` — softmax temperature
- `top_p` — nucleus sampling
- `top_k` — top-k sampling

**To Add:**
- `min_p` — minimum probability threshold
- `presence_penalty` — penalize tokens that already appeared
- `frequency_penalty` — penalize proportional to token count
- `repetition_penalty` — multiplicative penalty for repeated tokens

**Implementation:** Modify logits before softmax:
```zig
// Presence penalty
for (tokens_already_appeared) |token_id| {
    logits[token_id] -= presence_penalty;
}

// Frequency penalty  
for (token_counts) |count, token_id| {
    logits[token_id] -= frequency_penalty * @intToFloat(f32, count);
}

// Repetition penalty (multiplicative)
for (recent_tokens) |token_id| {
    if (logits[token_id] > 0) {
        logits[token_id] /= repetition_penalty;
    } else {
        logits[token_id] *= repetition_penalty;
    }
}
```

**Complexity:** LOW

#### 5.4 Logit Bias

**OpenAI Spec:** `logit_bias: map<token_id, bias>` — add bias to specific token IDs.

**Use Cases:**
- Force JSON output (bias up `{`, `}`)
- Suppress unwanted tokens
- Brand voice enforcement

**Complexity:** LOW

#### 5.5 Multiple Completions (n > 1)

**OpenAI Spec:** `n: integer` — generate N independent completions.

**Impact:** Increases inference cost linearly. Not recommended for streaming.

**Complexity:** MEDIUM (requires parallel generation or sequential with state management)

#### 5.6 Response Format (JSON Mode)

**OpenAI Spec:** `response_format: {type: "json_object"}` or JSON Schema

**Implementation Options:**

| Approach | Complexity | Quality |
|----------|------------|---------|
| Post-process (validate JSON) | LOW | Poor (may not generate valid JSON) |
| Constrained decoding (grammar-based) | HIGH | Good (guarantees valid JSON) |
| Outline-style guided decoding | MEDIUM | Medium (regex-based constraints) |

**Recommendation:** Defer until grammar-based constrained decoding is viable.

### 6. Performance Optimizations

#### 6.1 Speculative Decoding

**Value Proposition:** 1.5-2.8x speedup by using a smaller "draft" model to predict tokens, then verifying with the main model in parallel.

**How It Works:**
1. Draft model (e.g., 1.5B) generates N tokens quickly
2. Target model (e.g., 7B) verifies all N tokens in a single forward pass
3. Accept verified tokens, reject others, repeat

**Requirements:**
- Draft model compatible with target model (same tokenizer, similar architecture)
- Memory for both models (or fast draft model loading)

**Draft Model Selection:**

| Target Model | Draft Model | Speedup |
|--------------|-------------|---------|
| Qwen2.5-7B | Qwen2.5-1.5B | 1.5-2.0x |
| Llama-3.2-8B | Llama-3.2-1B | 1.5-2.2x |
| Phi-4 | Phi-3-mini | 1.3-1.8x |

**Configuration:**
```json
{
  "model": "qwen2.5-coder-7b",
  "draft_model": "qwen2.5-coder-1.5b",
  "num_draft_tokens": 4
}
```

**Complexity:** HIGH (requires two model instances, token acceptance logic)

#### 6.2 Continuous Batching

**Value Proposition:** Increase throughput by processing multiple requests together in a single batch.

**Feasibility for zlx:** LOW — Not recommended  
**Reasoning:** 
- MLX uses single Metal command queue
- Continuous batching requires dynamic batch formation and attention mask management
- Memory fragmentation with varying prompt lengths
- Diminishing returns for single-user personal server

**Alternative:** Keep mutex-serialized inference; add request queue with 503 on overflow.

#### 6.3 Quantization Improvements

**Already Supported:** 4-bit MLX models via MLX-community

**To Add:**
- 3-bit and 2-bit support (if MLX adds support)
- Dynamic quantization (quantize less important layers more aggressively)

### 7. Model Management

**Value Proposition:** Automatic model discovery, download, and organization. Eliminates manual model placement in `./models/`.

#### 7.1 HuggingFace Integration

**Features:**
- Search HF Hub for MLX-compatible models
- Auto-download from `mlx-community/` organization
- Resume interrupted downloads
- Verify checksums

**API:**
```
GET  /v1/models/hub/search?q=qwen2.5-coder   # Search HF Hub
POST /v1/models/hub/download                 # Download from HF
     { "repo_id": "mlx-community/Qwen2.5-Coder-7B-Instruct-4bit" }
```

**Authentication:**
- HF token in `~/.zlx/config.json` or env var `HF_TOKEN`
- Anonymous access for public models (rate limited)

#### 7.2 Model Registry

**Persistent model catalog:**
```json
// ~/.zlx/models.json
{
  "models": [
    {
      "id": "qwen2.5-coder-7b",
      "path": "~/.zlx/models/mlx-community/Qwen2.5-Coder-7B-Instruct-4bit",
      "source": "huggingface",
      "repo_id": "mlx-community/Qwen2.5-Coder-7B-Instruct-4bit",
      "size": "4.5GB",
      "downloaded_at": "2026-03-30T12:00:00Z"
    }
  ]
}
```

#### 7.3 Model Organization

**Directory Structure:**
```
~/.zlx/
├── models/
│   ├── mlx-community/
│   │   └── Qwen2.5-Coder-7B-Instruct-4bit/
│   │       ├── config.json
│   │       ├── tokenizer.json
│   │       └── *.safetensors
│   └── local/
│       └── my-custom-model/
├── cache/
│   └── <model_hash>/
│       └── <prompt_hash>.cache
└── config.json
```
