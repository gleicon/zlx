# Research Summary: zlx v1.1 Features

**Project:** zlx — Zig LLM Inference Server v1.1  
**Domain:** Advanced features for local LLM inference on Apple Silicon  
**Researched:** 2026-04-01  
**Overall confidence:** HIGH (stack and architecture patterns verified; TurboQuant implementation path identified)

---

## Executive Summary

This research documents the ecosystem landscape for seven feature categories targeted for zlx v1.1: TurboQuant KV-cache compression, multi-model support, prompt caching, Web UI integration, API improvements, performance optimizations, and model management. The research confirms v1.1 is technically viable within the existing Zig + MLX.zig + httpz stack, with the most significant work being TurboQuant Metal kernel extraction and integration.

Key finding: TurboQuant (arozanov/turboquant-mlx) is confirmed Python-only, but the Metal kernel source strings are embedded in the repository (`metal_kernels_v2.py`) and can be extracted for standalone compilation. This path — extracting MSL source and compiling via `xcrun metal` — is the recommended approach rather than attempting Python bindings or full reimplementation.

For Web UI, the research strongly recommends **not building a custom UI**. Instead, integrate with Open WebUI (46K GitHub stars), which is already OpenAI-compatible. Users simply point Open WebUI at zlx's API endpoint. This eliminates 1000+ lines of frontend code and build complexity while providing a superior user experience.

The architecture for v1.1 adds six new components to the existing four-file structure: model manager, KV cache persistence, TurboQuant integration, speculative decoding, sampling pipeline, and download manager. All components follow established patterns from mlx-lm server, llama.cpp, and vLLM.

## Key Findings

### Stack
**Core stack unchanged:** Zig 0.13.0, MLX.zig submodule, mlx-c 0.1.2, httpz zig-0.13 branch. No version upgrades needed or recommended.

**New technologies to add:**
- Metal shader compilation pipeline (`xcrun metal`, `xcrun metallib`)
- MLX `mlx_save`/`mlx_load` for KV cache persistence
- `std.http.Client` for HuggingFace Hub integration
- Open WebUI (external integration, not in-tree)

### Architecture
**Core principle maintained:** Single static binary, no Python runtime. v1.1 features fit within this constraint.

**Major new components:**
1. **model_manager.zig** — Model registry, lifecycle management, memory budget enforcement
2. **kv_cache.zig (expanded)** — Strategy pattern for standard / TurboQuant / persistent backends
3. **turboquant.zig** — Extracted Metal kernel integration
4. **cache_persistence.zig** — KV cache save/load via MLX native functions
5. **sampling.zig** — Centralized sampling parameter pipeline
6. **spec_decode.zig** — Speculative decoding with draft model
7. **download.zig** — Background HF Hub download manager

**Critical pitfall for architecture:** Model switching requires rigorous MLX cleanup (`mlx_array_free`, `mlx_synchronize`) or OOM will occur. The memory budget check must include 50% overhead for KV cache and temporaries.

### Features
**Priority 1 (Table stakes / API compatibility):**
- Stop sequences — currently only EOS, need string matching
- Logprobs — track top-k logits during sampling
- Temperature, top_k, top_p, min_p, penalties — MLX.zig supports, need API exposure

**Priority 2 (Differentiators):**
- TurboQuant KV compression — 4.6x memory reduction
- Prompt caching — sub-second TTFT for repeated contexts
- Multi-model hot-swap — without server restart
- Speculative decoding — 1.5-2.8x speedup with compatible draft model

**Priority 3 (Convenience):**
- Model auto-download from HF Hub
- Open WebUI integration (external)

**Anti-features (still not building):**
- Custom Web UI — integrate Open WebUI instead
- Continuous batching — not beneficial for single-user server
- PagedAttention — vLLM optimization, not applicable to MLX unified memory
- Vision/multimodal — out of scope

### Pitfalls
**Critical (could block release):**
1. **TurboQuant kernel extraction** — MSL source embedded in Python; requires careful extraction and testing
2. **Model cleanup on switch** — MLX memory not released properly causes OOM
3. **Cache key collisions** — must include model hash in cache key
4. **Memory budget miscalculation** — need 50% overhead for KV cache

**Moderate (fixable with effort):**
- CORS headers for Open WebUI integration
- Sampling parameter conflicts (temperature=0 + min_p > 0)
- Download blocking inference (must be background thread)

## Implications for Roadmap

Based on research findings, suggested phase structure for v1.1:

### Phase 1: API Improvements (Foundation)
**Rationale:** These are table stakes for OpenAI API compatibility. Low complexity, high user value. Builds on stable v1.0 foundation.

**Delivers:**
- Full stop sequence support (string matching)
- Logprobs tracking and response
- Sampling parameters: top_k, min_p, presence_penalty, frequency_penalty, repetition_penalty, logit_bias

**Addresses:** Stop sequences pitfall (simple string matching), sampling conflicts (validation layer)

### Phase 2: Multi-Model Support
**Rationale:** Requires solid foundation but is independent of inference changes. Memory management is the primary complexity.

**Delivers:**
- Model registry (scan + metadata)
- Hot-load / hot-unload with proper MLX cleanup
- Memory budget enforcement
- Model aliases (`--served-model-name`)

**Addresses:** Model switching OOM pitfall (rigorous cleanup protocol)

### Phase 3: Prompt Caching
**Rationale:** Builds on KV cache layer. Orthogonal to multi-model (cache is model-specific). High value for agentic use cases.

**Delivers:**
- Cache key generation (SHA-256 of model_hash + prompt)
- `mlx_save` / `mlx_load` integration
- LRU eviction with size limits
- API endpoints: cache management

**Addresses:** Cache key collision pitfall (model hash inclusion), unbounded cache growth (LRU eviction)

### Phase 4: TurboQuant Integration
**Rationale:** Most complex feature. Requires Metal kernel extraction, compilation pipeline, and drop-in KV cache replacement. Defer until core features stable.

**Delivers:**
- Metal kernel extraction from turboquant-mlx
- `build.zig` integration for `.metallib` compilation
- TurboQuantKVCache backend implementing standard interface
- Layer-adaptive mode (first/last N layers FP16)

**Research flag:** Requires dedicated research sub-phase for kernel extraction and standalone testing.

**Addresses:** TurboQuant extraction pitfall (independent testing), Metal kernel crash risk

### Phase 5: Performance Optimizations
**Rationale:** Speculative decoding is a significant speedup but requires compatible draft model selection and adds complexity. Defer until v1.1 core is stable.

**Delivers:**
- Speculative decoding with draft model
- Acceptance rate metrics and auto-disable
- Draft model compatibility checking

**Addresses:** Speculative decode mismatch pitfall (compatibility validation)

### Phase 6: Model Management
**Rationale:** Nice-to-have convenience feature. Background download requires threading but doesn't affect inference core.

**Delivers:**
- HuggingFace Hub integration
- Background download with progress
- Resume support and checksum verification

**Addresses:** Download blocking pitfall (background thread), CORS for Open WebUI

---

## Phase Ordering Rationale

- **Phase 1 (API Improvements) first:** These are table stakes. Many clients expect logprobs and stop sequences. Low risk, immediate value.

- **Phase 2 (Multi-Model) before Phase 3 (Caching):** Multi-model establishes the model lifecycle and memory management patterns that caching builds upon. Cache is model-specific.

- **Phase 3 (Caching) before Phase 4 (TurboQuant):** Both touch KV cache layer. Get caching working with standard FP16 cache first, then add TurboQuant backend.

- **Phase 4 (TurboQuant) after core features:** Highest risk due to Metal kernel extraction. Don't block other features on this.

- **Phase 5 (Speculative Decode) after TurboQuant:** Speculative decode can use either standard or TurboQuant cache. Let TurboQuant stabilize first.

- **Phase 6 (Model Management) last:** Pure convenience feature. Background download is independent of inference quality.

## Gaps to Address

1. **TurboQuant Metal Kernel Extraction:** Need hands-on extraction and compilation test. This is the only blocking research item.

2. **Speculative Decoding Draft Model Pairs:** Need to document which draft models work with which targets. Can be done during implementation.

3. **Cache Size Heuristics:** What's a reasonable default cache size (10GB?)? Depends on user hardware patterns. Start with configurable, gather data.

4. **Memory Budget Formula:** The 50% overhead ratio is conservative. Could be refined with profiling on M4/M5 hardware.

5. **Open WebUI Integration Testing:** Verify CORS headers and full compatibility. Low risk but needs verification.
